# v1.4 prompt delivery and idle/review hot-path closure

Reviewed baseline: `3085bb1b6d74e1cc37b8f4b593896da65937b2f9`.
The initial materialized source tree was verified against
`96c90ab2e41b6e771ab72b4d0db2f3b4af07965c` before editing.
This work stays within the frozen defect/performance/qualification scope.
`stableReady=false` and `publicationAllowed=false` are unchanged.

## Prompt acknowledgement is not ownership of the current draft

The old reducer unconditionally cleared a thread's current draft when an asynchronous
submission acknowledgement arrived. It could delete text entered after submission,
including a draft edited and then changed back to its original text. Re-entering the
composer while the first send was pending could enqueue another turn, and a successful
acknowledgement still left the old turn snapshot usable for a subsequent submission.
Four regression cases reproduced these behaviors before correction.

A bounded, transient ticket table now permits one pending submission per thread and
at most 32 per application instance. The ticket follows the internal effect, command,
queue rejection and success/failure event. It is not sent as a Codex protocol field,
not a remote idempotency key, and not persisted as another copy of the prompt.
Matching acknowledgement clears a draft only when none of its production editing
paths ran after submission. Tickets never wrap or alias on counter exhaustion.

Stale, duplicate, cross-thread or otherwise unmatched receipts do not clear drafts
or complete a newer submission. Rejected/failed sends preserve the draft. Successful
submission waits for the actor's authoritative history refresh before allowing the
next send, so a stale idle/active-turn snapshot cannot authorize a new turn. Failed
or uncertain outcomes are not retried automatically; the existing explicit history
refresh and operator decision remain necessary. This is per-process fencing, NOT
exactly-once delivery across network failures, restart, multiple TUI instances or
other clients. Process termination can leave a retained draft requiring reconciliation.

## Disabled notifications do no projection work

Previously Off mode constructed complete notification observations, compared them and
retained registry/runtime maps at startup and every accepted planning installation.
It skipped only delivery. Off is fixed for the RuntimeNotifications instance; there is
no live Off-to-On mode transition requiring those snapshots to be kept warm.

Seed and observe now return before observation construction in Off mode. Two negative
regressions showed the original disabled instance retaining historical runtime states;
both pass after the change. Enabled-mode edge tracking, delivery queue capacities and
failure notices remain unchanged. Removing this work is an algorithmic cost reduction,
not a measured human-time or token-savings percentage.

## Review CPU work is not input-thread work

The old Git-event drain called syntax prewarming directly on the input thread. The
shared lazy cache could also initialize syntax assets or wait on its mutex during a
render lookup, and the UI fallback recomputed word-level diff on cache misses.

Prewarming now executes through spawn_blocking inside the existing Git actor task
budget (at most eight outstanding tasks, including work waiting for presentation).
No separate unbounded work queue is added. Oversized raw diff payloads skip syntax
prewarming before asset initialization or word-pair work. Cache lookup uses OnceLock
get and Mutex try_lock, never constructing assets or waiting for a busy writer.
Cache-unavailable/over-budget word diff is visibly reported as plain diff, not silently
advertised as a successfully rendered word diff. The rendered raw diff is preserved.

The regression set includes a controlled lock-contention handshake, a real TestBackend
render of a cold word-diff request, and a source-bound prohibition on input-drain
prewarming. These fail against the corresponding prior behavior and pass after repair.
The handshake's timeout is a test liveness bound, not a terminal latency SLO.

Raw diff formatting and copying are still bounded by the existing Git capture limits,
not certified below 50 ms. Once started, blocking CPU work is not forcibly cancelled;
this change does not promise a new process-exit or power-loss guarantee. Existing
state recovery, migration and real terminal qualification requirements remain.

## Verification and maintained boundaries

The original nine targeted failing checks and the corrected suite are retained with
the audit evidence. Additional cases cover matching/replayed acknowledgements,
wrong-ticket failures, pending capacity, draft persistence, navigation, paste and
explicit retry after refreshed history. Full locked/all-target/all-feature tests,
Clippy with denied warnings, formatter, Python archive/qualification regressions and
both existing module ratchets are checked before integration.

Only the new prompt modules receive new explicit size ceilings; no previous ceiling
is raised. No Cargo dependency, protocol wire schema, durable storage schema, migration
policy, account credential, release authorization or historical checkpoint is changed.
Temporary candidate transport files and workflow are excluded from the final source
tree. Final PR checks and fresh-main native previews are separate evidence stages.
Synthetic benchmarks and duration tests remain source-bound diagnostics, not real
terminal/network/account or multi-hour production certification.
