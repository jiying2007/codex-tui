# v1.4 Review result-install consistency

Baseline: `fb26bd084fcb39bade4c26b32c3733a07e2c9dea` (#223).

## Defects and bounded correction

A GitReview result previously changed the global file cursor even when it belonged
to another thread. It also accepted a result from a former cwd or an unknown thread,
and kept a numeric cursor when the refreshed file order changed. Removing the
selected file or receiving an empty review left an unrelated scroll offset in place.

The result-install boundary now checks the live thread and exact cwd first. Only
the active Review updates selection, preserving the exact selected path when it is
still present. A removed/renamed selection clamps safely and resets scroll. Valid
background results still enter the existing four-entry cache without evicting the
active Review. No new persistent state, duplicate cache or Git/API call is added.

Eight deterministic reducer tests cover six previously failing behaviors, a same-
file refresh positive case and cache protection under background arrivals. The
remote verification keeps a failing-before log and a complete passing-after suite.
The temporary verification workflow must be absent from the merged source tree.
The existing module ceilings and Cargo lock remain unchanged.

## Boundaries

This is a file-selection and result-target correction, not per-request ordering for
same-cwd Git reads or an atomic snapshot of a concurrently changing worktree. Exact
path identity does not infer file identity across renames. Existing mutation
revalidation, source authority, protocol compatibility and release gates remain.

No local-container test result is claimed in this audit. GitHub native CI and the
post-merge preview verify their exact source identities. Real account/internal
GitLab/Windows-SSH controlling-terminal checks remain external; stableReady and
publicationAllowed stay false. No stable release or human/token-savings claim.

Candidate runs `37264750708` and `37265173589` reproduced all six defects, then
exposed cache and render fixtures whose incoming cwd did not match their thread
metadata. The fixtures now assign the cached/incoming cwd to the live threads;
all cache and no-synchronous-render assertions remain. Both failed runs are
retained as failures. No production guard or test assertion was weakened.
