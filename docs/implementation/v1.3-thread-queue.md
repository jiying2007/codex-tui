# v1.3 Thread Queue

Status: implementation

Thread Queue is an upstream-authoritative projection of the experimental Codex
App Server queue API. codex-tui does not persist a second queue.

## Entry and controls

Open from a Thread with `q` or the command palette.

- `j/k`: select queued submission
- `n`: add a text submission
- `e`: edit a text-only submission
- `[` / `]`: reorder selected item
- `s`: start selected submission
- `x`: delete selected submission
- `r`: refresh from App Server
- `q` / `Esc`: close and stop watching the queue

Start and delete require an explicit `y` confirmation; `c`/`Esc` cancels.
Add/edit use Enter as the explicit submission action. Reorder is reversible and
is immediately followed by an authoritative list refresh.

## Authority and synchronization

Supported upstream methods:

- `thread/queue/list`
- `thread/queue/add`
- `thread/queue/update`
- `thread/queue/delete`
- `thread/queue/reorder`
- `thread/queue/start`

While open, `thread/queue/changed` triggers a fresh upstream list. Every local
mutation also reloads the queue before the UI accepts the new snapshot.

The App Server connection opts into the experimental API because both Queue and
full-history transcript search are currently experimental upstream capabilities.
Older servers fail soft: Queue becomes unavailable without affecting ordinary
Thread/turn operation.

## Multimodal safety

Queue entries preserve upstream input values in memory. Entries containing
image/audio/skill/mention or other non-text input remain visible and can be
started, deleted or reordered. codex-tui deliberately disables the text editor
for those entries rather than replacing the full upstream input with a text-only
payload.

No queue state is written to SQLite.
