# v1.4 Core Module Decomposition

Status: implementation

This work package is behavior-preserving. It closes the v1.4
`core-module-decomposition` requirement without changing any user-visible
workflow or upstream authority.

## Why these boundaries

The v1.4 workflow-completion features pushed two mature binary modules close to
their no-growth ceilings:

- `src/main.rs`: startup, Doctor diagnostics, event loop, actor drains and
  effect execution lived together.
- `src/runtime_input.rs`: terminal focus, modal input priority, Command
  Palette behavior, command-to-reducer mapping and ordinary key routing lived
  together.

The decomposition follows existing runtime responsibilities instead of
introducing a new framework.

## Extracted responsibilities

### `runtime_commands.rs`

Owns the single `Command -> Action` mapping and the thin reducer dispatch.
Help/keymap/Command Palette tests continue to exercise this exact mapping.

### `runtime_palette.rs`

Owns Command Palette-specific typed/pasted input and key behavior. The palette
still snapshots its contextual command set in `app/palette.rs`; this module
only routes input to that state and executes the selected command through
`runtime_commands`.

### `runtime_doctor.rs`

Owns human-readable Doctor diagnostics for store, Git, Forge, terminal,
presets and Codex/App Server targets. It does not own release qualification or
support-bundle authority.

## Ratchet changes

This extraction intentionally tightens the mature-module ceilings instead of
raising them:

- `src/main.rs`: 2200 -> 1900
- `src/runtime_input.rs`: 450 -> 300

New bounded modules receive explicit no-growth ceilings:

- `src/runtime_commands.rs`: 180
- `src/runtime_palette.rs`: 160
- `src/runtime_doctor.rs`: 380

At extraction time the large modules fall from roughly:

- `main.rs`: 2153 -> ~1830 lines
- `runtime_input.rs`: 435 -> ~270 lines

## No-regression contract

This work must not weaken or reinterpret:

- v1.3 full-history transcript search;
- upstream-authoritative Thread Queue;
- named local/remote App Server targets;
- GitHub plan-confirm-revalidate-receipt mutations;
- v1.4 Board viewport, WorkCard relationships, thread lifecycle, metadata
  search, Saved View editor, Review evidence/external-open, long-thread
  viewport cache or fuzzy Command Palette.

Canonical CI, Rust 1.88, scale evidence and the existing executable UI/keymap
contracts remain the evidence authority.

## Complete ratchet coverage follow-up

The original v1.4 ratchet inherited mature-module ceilings and added ceilings for
newly extracted modules, but the checker only validated entries already present in
the plan. A source file that was never listed could therefore grow without
participating in the no-growth contract.

The active v1.4 plan now requires complete `src/**/*.rs` coverage. Every current
Rust source module has an explicit ceiling, including previously unlisted legacy
and support modules. The checker fails if a new Rust source file appears without a
plan entry. Historical predecessor plans keep partial coverage semantics so v1.4
files do not retroactively invalidate their frozen checkpoints. The 30 previously
unlisted files are baselined at their current line counts, and every pre-existing
v1.4 ceiling is tightened from its development budget to the current completion
state. No ceiling is increased. This turns the completed v1.4 plan into a literal
post-completion ratchet while preserving historical plan semantics.
