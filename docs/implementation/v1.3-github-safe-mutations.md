# v1.3 Safe GitHub Mutations

Status: implementation

GitHub writes reuse the existing Forge mutation authority and receipt model; no
second mutation engine or headless write surface is introduced.

## Supported operations

From Review / Workspace context actions:

- create pull request;
- comment on pull request;
- approve pull request;
- merge pull request.

The normalized internal names still use `MergeRequest` for compatibility with
the existing Forge contract, but user-facing text is provider-neutral.

## Safety contract

Every write follows the same sequence as GitLab:

1. construct an exact `ForgeMutationPlan`;
2. retain only non-secret plan metadata (comment body length, never the body);
3. require explicit user confirmation;
4. re-read repository/change-request identity and preconditions;
5. for approve/merge, read the exact GitHub `head.sha`;
6. immediately before the write, read the pull request again and require the
   same HEAD SHA;
7. execute one GitHub API mutation;
8. read back the result;
9. persist a success receipt, or move to `OutcomeUnknown` and reconcile.

An uncertain create can be proven only when exactly one open pull request has
the planned source/base/title. An uncertain approval is proven only when the
authenticated user's latest review is APPROVED. An uncertain merge is proven
only when GitHub reports `merged=true`. Comment payloads intentionally leave
memory after execution, so uncertain comments remain unknown and are never
blindly retried.

## Merge policy

The GitHub merge call supplies only the planned exact `sha`. codex-tui does
not send force, bypass, admin override, or merge-policy override fields.
Repository branch protection and GitHub merge policy remain authoritative.

## Authentication and provider identity

GitHub operations use the existing authenticated `gh api --hostname HOST`
transport. The repository API must re-confirm both the numeric repository ID
and exact `owner/repo` path captured by the Forge projection.

This capability does not add GitHub Enterprise auto-detection. Custom hosts
continue to enter the GitHub provider only through the existing explicit
provider/authentication routing.

## Non-goals

- no headless mutation commands;
- no automatic approval or merge;
- no retry of uncertain writes;
- no force/bypass;
- no stored GitHub token;
- no separate GitHub task/workflow database.
