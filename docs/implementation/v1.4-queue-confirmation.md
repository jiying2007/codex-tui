# v1.4 queue confirmation and payload integrity

Baseline: `4a02b3538a344fd7a732b44f0d1212d24373064f` (#230).

This frozen-scope audit checked the mutation coordinators and their confirmation
routing, queue reads/edits, prompt submission fencing, store shutdown, source-triggered
preview and sustained-test paths. It preserves the previous editor/menu/read fixes.
The newly reproduced defects are in queue confirmation and queue payload ingestion.

## Confirmation is bound to the original item

Start/delete previously stored only a mutation kind and item ID. A changed payload,
replacement client identity, removed item/thread, wrong thread snapshot, or failed/
in-flight refresh could still dispatch the old confirmation. The dialog did not name
the original item. A typed ephemeral confirmation now retains one original item;
confirm requires the same live thread, open/ready queue and complete unambiguous
snapshot, with identical upstream item ID, client ID and raw input. Derived summary
formatting is not mutation authority. Invalid confirmations send nothing and require
refresh/reconfirmation. Cancellation, close and reopening release the confirmation.

The dialog identifies the original item even when the list selection changes. A
successful confirmation emits one request and marks the queue pending refresh; it
cannot be repeated by pressing confirm twice. An unchanged item survives an unrelated
reorder/navigation. No full-queue copy, new persistent state, RPC or dependency is added.
The old ID-only pending-mutation field is replaced, not retained as a compatibility shim.

## Do not flatten input that the text editor cannot preserve

Items carrying nonempty textElements, unknown semantic text fields, malformed text
or malformed elements remain readable with their original raw input, but are not
plain-text editable. Empty input is likewise not declared editable. The optional
older shape without textElements and unknown outer envelope fields remain supported.
Ordinary plain text editing still uses the existing API; this does not invent new
upstream input semantics or drop unknown fields from the retained observation.

Pages reject empty identifiers, duplicate item IDs, invalid cursor types and more
than the requested 100 items. Complete lists reject duplicates across pages and
invalid/incomplete snapshots before UI installation. Repeated cursors are rejected
before another request. The existing ten-page/1,000-item bound is unchanged and its
constant has one owner. No partial list becomes authority for a reorder or confirmation.
The same ready-snapshot accessor also guards starting/committing edits and reordering;
a failed or in-flight refresh cannot authorize mutations using an older cached list.
An independent Add to the same live thread does not require a loaded queue list.

## Reproduction and regression

There are 30 new tests: production reducer/render cases, payload parsing, and a local
WebSocket peer driving the real RpcSession pagination path. Against the original
production baseline they produce 24 failures and six positive passes. After repair,
all 578 Rust and 34 Python tests, formatting, Clippy -D warnings and original module/
plan/completion checks pass locally. Native PR and final-main qualification remain
separate required verification; no candidate timing is relabelled as final evidence.

The first full local candidate run failed four source-layout regression checks because
the new test-module declaration introduced an early cfg(test) marker. Moving only
that declaration after production/tests restored the existing production-source
inspection boundary; no assertion or production check was removed. This failure is
retained. An existing queue confirmation fixture now delivers the upstream refresh
between consecutive mutations rather than treating an in-flight reorder/start as
acknowledged; its dispatch, confirmation and cancellation assertions remain.

New helper/test module ceilings are 150/140 lines; no previous ceiling increases.
No Cargo/schema/credentials/publication change. Temporary transport/verifier files
must not enter final source or squash history. Real account/internal GitLab and
Windows-SSH controlling-TTY qualification remain external; stableReady and
publicationAllowed stay false.

These guards compare the latest local observation, not server-side compare-and-swap.
Remote changes after that observation can race; existing queue RPC outcome/retry
semantics are unchanged. Five-minute synthetic soak and CPU/TestBackend distributions
are not multi-hour leak certification, terminal input-to-pixel SLO or human/token ROI.
