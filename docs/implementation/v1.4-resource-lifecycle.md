# v1.4 external child ownership and resource closure

Baseline: `19482044d0e73512da6f5d45bf501ddd6b005c00` (#231).

## Audit scope and reproduced defect

This continuation reviewed the current queue confirmation/read/editor fences,
store result and shutdown paths, registry/conversation observations, external
handoffs, and subprocess ownership. Existing #226-#231 protections are retained;
there is no new product line or claim that all conceivable defects are excluded.

Launch presets and external editor/browser handoffs called `std::process::Command`
and then dropped `Child` without waiting. On Linux, completed children remained
zombies for the lifetime of the TUI. Three real-process regressions reproduce this
on the original paths: one launches four short-lived presets; two exercise the
actual editor/browser adapters in isolated child test processes. They inspect
`/proc` without reaping before making the observation, then clean up baseline
zombies after recording the failure. No desktop application or network is used.

## Bounded production correction

All three handoff paths share one lazy standard-library reaper. It owns at most
32 immediate child handles, retains the handle until `try_wait` confirms exit,
and releases its capacity for both successful and nonzero exits. At capacity,
the next handoff is refused **before any process is started**, with a visible
error through the existing launch/external-open error path. An OS spawn failure
consumes no slot. There is no fallible queue transfer after a successful spawn.

There is one worker, not one thread per child. While children exist it checks
at a 100 ms interval, also waking on new handoffs; while idle it sleeps on a
condition variable without polling. The lock only covers registration and bounded
nonblocking status checks, not an external program's lifetime. OS process creation
remains synchronous as before and is not claimed to have a strict latency bound.

A long-lived editor cannot prevent a finished browser helper from being reaped.
No child is killed, retried or given an automatic lifetime timeout. The existing
return value still means **started**, not **completed successfully**. Explicit
launch confirmation, argv handling, cwd and null stdio behavior are unchanged.
TUI exit does not wait for or terminate the external app; supervision does not
extend to grandchildren or survive the TUI process itself.

The worker retains ownership on status-check errors and refuses new handoffs
until that condition clears. Existing Tokio-managed Git/Forge/notification and
PTY-specific lifecycles are not moved into this helper or weakened.

## Verification and limits

Tests cover the three original resource leaks, capacity-before-side-effect,
capacity reuse, spawn failure, nonzero exit, long/short child coexistence,
concurrent admission, and supervisor teardown without killing children. Native
helper tests use the Rust test executable with per-child environment variables,
not process-wide environment mutation. Linux adapter tests also check that a path
with spaces and a URL with query punctuation arrive as one argument unchanged.

No Cargo lock/dependency, persistence schema, RPC, security ignore, manual PASS,
stable authority or publication condition changes. Existing module ceilings stay
unchanged; the new helper and its tests have explicit bounded ceilings. Source
capture and candidate transport workflows must be absent from the merged tree.

This correction prevents observed unreaped-child accumulation. It does not certify
whole-program leak freedom, multi-hour real-account stability, terminal input-to-
pixel SLO, or measured human/token savings. Real account/internal GitLab and
Windows-SSH controlling-TTY qualification remain external exact-SHA requirements.
The package remains a non-publishing preview until separately authorized.
