# v1.4 mutation intent and open-menu consistency

Baseline: `e46badac9678b4df73eeba272a647a34b51d03af` (#229).

## Audit and reproduced failures

This review checked the current async read fences, queue and prompt editors,
operator-state recovery, command dispatch, menu/editor transitions and source-bound
preview gates. It preserves #226-#229 rather than reimplementing their protections.
There is no new product scope, persistent schema, dependency, RPC or publication
permission. Existing migration, recovery and mutation preflight/receipt contracts
remain regression-covered.

The remaining pre-plan input paths resolved their target again at commit. A Forge
comment or new change-request title could follow another thread, repository or
change request; worktree creation/deletion could follow a changed repository;
a Goal draft could overwrite an externally changed objective or recreate a cleared
Goal. Shortcut binding retained only a boolean and could bind a neighbouring item.
An open context menu also recomputed its choices and targets on each refresh.

The 24 production-reducer regressions produce **19 behavior failures / 5 positive
passes** on the exact original baseline. They cover editor retargeting, liveness,
repo/provider/host/path/default-branch/IID changes, Goal replacement/clear, shortcut
identity, menu choice changes and ordinary unchanged-target/cancel/confirmation
paths. Multiple identity fields are additionally exercised as subcases.

## Bounded correction

`mutation_editor` records one ephemeral typed target when an editor opens and
compares that identity before every step commits. A mismatch keeps the text and
worktree wizard fields, displays a bilingual refusal and creates no operation.
Only selection-relevant identity is compared: Forge title/observation refresh and
Goal token/time accounting do not invalidate otherwise safe edits. Goal objective
and creation identity are checked, while existing Goal status remains unchanged.
Successful completion and explicit input cancellation release the editor snapshot.

The shared Forge target lookup also requires a live thread and matching, healthy
Git/Forge cwd observations. Shortcut binding stores the original SourceRef itself
rather than a duplicated boolean/target pair and refuses a removed target.

`context_menu` freezes choices and the local/view/Forge/worktree target at open.
Rendering/navigation keep the original highlighted action. Execution requires the
original target, a still-available action and matching repository/change-request
scope; otherwise the menu closes with a refusal. Immediate reducer invocations
without an open menu still resolve live choices; they do not represent a delayed
menu selection. Closing/backing out clears all ephemeral menu data.

Guards run on menu open/execute and editor commit, not each keystroke or polling
cycle. They do not start external calls or traverse transcript history. The two
helpers have explicit 220/150-line ceilings; existing module ceilings are unchanged.

## Verification and evidence boundary

An isolated offline checkout was reconstructed from a source bundle whose download
SHA-256 matches GitHub. Rust/compiler and vendored dependencies came from retained
workflow artifacts; compilation used locked offline dependencies. The complete
source is further checked by canonical native CI before protected squash merge,
then by exact-main qualification, sustained soak and non-publishing native archives.
Temporary source capture and candidate transport files must not enter the final tree.

The initial full corrected local run found two old fixtures with synthetic live
thread cwd different from their Git context. The fixture cwd values were aligned;
all launch/plan/confirmation assertions were retained. The failed run is preserved,
not relabeled as successful verification. A later local replay reused one Cargo
output directory across the original and corrected worktrees and ran a stale
integration binary. That failed replay is retained; the corrected package is
clean-rebuilt, and final GitHub checks use independent checkouts. No assertion or
product guard is disabled to accommodate the harness.

These are local observation/intent checks, not server-side compare-and-swap,
exactly-once mutation execution, atomic worktree snapshots or guarantees against a
remote change after the last observation. Existing confirmation and execution-time
revalidation remain required. Restoring SQLite remains offline-only; five-minute
synthetic soak is not multi-hour real-account leak certification. No terminal SLO,
human-hours or token-savings percentage is inferred from these tests.

Real Codex account/internal GitLab and Windows-SSH controlling-TTY observations
remain external. `stableReady=false` and `publicationAllowed=false` are unchanged.
