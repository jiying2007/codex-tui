# v1.4 first-deployment baseline — no predeployment upgrade promise

Decision: 2026-10-08. v1.0.0 exists as a published GitHub Release, but the
maintainer reports that neither v1.0.0 nor v1.4.0 has been put into service.
The next v1.4 candidate is therefore the first deployment baseline.

## Removed compatibility surface

- No automatic import of a prior `state-v1.json` operator state file.
- No startup backup/rename/migration of predeployment JSON state.
- No legacy import marker in store health, Doctor or compatibility reports.
- First installation creates SQLite v4 directly; earlier, never-deployed v1-v3
  SQLite schema images and recovery sources are refused without rewriting data.
- No release-blocking fixture pretending a v1.0 deployment existed.
- No backward-upgrade requirement from v1.0, v1.1, v1.2 or v1.3 products.

Fresh installation initializes the current SQLite store. Arbitrary stale JSON
files are not consumed, modified or silently migrated; operators must explicitly
start from a fresh local state.

## Regression control for the first-deployment boundary

`scripts/architecture/check_first_deployment.py` runs in canonical CI,
development qualification and Release Gate. Negative fixtures prevent
old JSON/SQLite migrations, duplicate predeployment module ceilings
or weakened data-recovery checks from returning silently. Historical
v1.3 manifests remain audit context, never a current qualification gate.
This guard does not substitute for runtime or real-provider testing.

## Safety and interoperability that remain required

- Local configuration TOML and current operator-state envelope remain supported.
- Current Codex App Server capability negotiation and GitLab/GitHub providers
  remain separate *live interoperability*, not historic product compatibility.
- SQLite corruption and forward-schema refusal, bounded writes, online backups,
  recovery of damaged images and idempotent reopen remain mandatory.
- Linux Tier 1 real Codex/Forge/controlling-TTY smoke, exact-SHA test evidence,
  protected main, immutable stable publication and explicit authorization remain
  blocking conditions. No hosted simulation is a real-terminal PASS.
- The released v1.0.0 tag, old release criteria, historical branches and
  reviewable audit records are not rewritten or destructively deleted.

Future *deployed* versions will need an explicit migration policy before
breaking their persisted storage or user-visible behavior. This decision only
retires compatibility with versions that were never deployed.
