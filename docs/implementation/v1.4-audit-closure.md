## Evidence boundaries and operating costs

The single v1.4 module ceiling ledger requires an explicit defect-maintenance review for touched or extracted modules. No parallel numeric ledger is introduced. Current Git compatibility, protocol fallback, plan/confirm/receipt mutations and uncertain-outcome rules remain supported. Undeployed legacy JSON/SQLite migration is not a requirement: first installation uses current SQLite v4 and refuses older or future schemas without destructive reset.

The UI snapshot/copy and result-install phases are measured, not claimed free.
The background worker removes database waits and planning computation from input
processing, but this does not certify a 50 ms end-to-end terminal SLO. Startup store
discovery and user-configured external services still require separate environment
qualification. Retained timing distributions are diagnostic; noisy hosted wall-clock
values are not silently promoted into hard release thresholds.

The package ABI baseline does not imply every peripheral/toolchain on Ubuntu 20.04
is supported or that an obsolete OS is recommended for production. It is an explicit
minimum libc contract, checked on extracted archives before release aggregation.

## Reviewed repository cleanup

The retained cleanup plan was generated by run `37225393660` and applied by
run `37225556814`. The exact-head, atomic lease-protected operation deleted
147 branches and verified 50 remaining branches. No active PR, protected branch,
release checkpoint or unproven branch was deleted. The proof covers 134 identical
squash deltas and 13 merged heads reachable from main. The receipt SHA-256 is
`0158b0085ba0dfb4a0e6b38e44d22e061a38678f2ef3a2be1d3fe5adf510c0c8`.

Remaining historical branches are not treated uniformly. Release/archive/checkpoint
references remain retained by policy. Ordinary feature/hardening branches are eligible
only when the dry-run-first script can prove the exact current branch head is the head
of a merged same-repository pull request and either reaches current main directly or
has a reachable squash merge with an identical complete raw tree delta.

Current PR-close hygiene still evaluates only the just-merged branch and requires
the exact merged-PR proof. In addition, a policy-change push to main that modifies the
hygiene workflow/script/tests performs one serialized full backlog re-evaluation using
branch-hygiene/v2, the same fresh-plan SHA-256 confirmation, atomic ref deletion and
force-with-lease checks.

The backlog-only v2 policy has one additional proof: an ordinary ephemeral branch
(`feat/fix/hardening/perf/refactor/rebase/chore/v1.2/v1.3/v1.4`) may be deleted when
its exact current HEAD is already an ancestor of current main, even if historical PR
metadata cannot prove an exact merged head. This is a no-unique-commit proof: deleting
the ref cannot make any commit unreachable from main. It is forbidden for the scoped
PR-close path, never applies to an open PR, and never applies to default/protected,
`release/`, `archive/`, `checkpoint/` or unknown-naming references.

This lets newly provable historical branches be removed without turning ordinary main
pushes into broad cleanup events. The retained plan/receipt artifact is mandatory and
records whether ancestor-only proof was enabled plus the eligible prefixes.

### Reviewed maintenance and resource boundaries

This is defect maintenance within the existing v1.4 freeze. The single
`release/v1.4-plan.json` module ledger records the reviewed limits for changed
modules and newly extracted modules; unchanged limits remain intact. Subscription
state and its wire fixtures are extracted under `app_server/subscriptions`.
Conversation row layout, sparse checkpoints and tests live under
`conversation_viewport`; the reducer delegates navigation to
`app/thread_navigation`. The upstream-convergence inventory includes the
conversation viewport, navigation, reading snapshot and request details modules.
No second ceiling ledger or exception switch is added.

The independent viewport review also found clipped approval scope and a lost
reading anchor after a recent-page refresh. Request details have a dedicated
local view and request-identity guard. A single paused reading snapshot is kept
only when a fresh page would discard the currently read item; authoritative
current-turn observations continue updating separately. Pagination results carry
their original cursor pair locally so a late response cannot join a stale page
to a new history boundary. The small event-routing and module additions required
for these defects are included in the same reviewed maintenance ledger.

The conversation cache remains revision- and width-bound to a 64–512 item window.
Long text stores a sparse row checkpoint every 128 display rows rather than one
heap object per newline. This bounds index growth while retaining all text in a
long loaded item. Viewport-size changes, prepended history and exact search hits
retain a turn/item/byte reading anchor. These properties do not establish a new
end-to-end latency or long-duration resource guarantee.

Paused older-history reading is labelled in the UI, retains its own pagination
boundary, and ends on follow, leaving the thread or thread removal. Repeated live
refreshes do not create a chain of snapshots. Request details support Home/End,
row/page navigation and Esc; these operations cannot approve or reject a request.

SQLite's read-only `quick_check` skips CHECK expressions in the tested bundled
SQLite version. The regression suite therefore keeps both a real non-`ok` result
row (a persisted NOT NULL inconsistency) and the original out-of-range hot-slot
case. Application CHECK invariants are validated before a writable connection
is admitted. Neither a successful SQLite scan nor these application checks are a
claim to detect every possible logical data error. Actual bootstrap decoding
failures also close admission for background workers.

### Evidence and remaining operational gates

Each CI/native receipt must retain its actual checkout SHA and binary checksum.
Local uncommitted-tree tests retain file and binary hashes and are identified as
development validation. A baseline SHA, a synthetic fixture or an older binary's
successful run must not be relabelled as the new candidate's release evidence.
Failed fixtures and their corrections remain in the review record. The temporary
execution environment reset after local validation, so prior local log files are
not part of the durable evidence bundle. Recovery verified the complete Git tree
hash against the saved source contents; fresh remote CI and its retained artifacts
provide the durable candidate and main evidence.

The repository's protection script is ready to require `security-gate`, but a
workflow or policy-file change does not itself update GitHub branch protection.
Application and read-back require a connection with repository administration
authority. Until that is verified, the missing live protection setting remains
an operational blocker, and the security result must be checked explicitly
before merging this remediation.

Real authenticated Codex L3, internal GitLab, Windows-to-SSH/Linux controlling-TTY
qualification and authorized release review remain tracked by issue #211 against
