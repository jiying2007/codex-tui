# v1.3 Remote App Server Targets

Status: implementation

## Authority

Target selection is local operator configuration. It does not create a codex-tui
daemon, shared target registry, cloud sync layer, or team authority. The selected
Codex App Server remains the conversation/runtime authority.

## Configuration

`[app_server].active` selects a named target. `local` is always available
implicitly and is equivalent to launching:

```text
codex app-server --listen stdio://
```

Configured transports:

- `stdio`: optional alternate Codex binary
- `websocket`: `ws://` or `wss://` client endpoint
- `unix-socket`: absolute Unix socket path

`--target NAME` overrides `active` for one invocation. `doctor codex`
uses the same resolution path and accepts the same override.

## Authentication

WebSocket targets may name `auth_token_env`. The token itself is read into
memory at startup and is never serialized into codex-tui TOML/SQLite/operator
state.

To prevent bearer-token disclosure over cleartext networks:

- `wss://` may carry a token;
- loopback `ws://localhost`, `127.0.0.0/8` or `::1` may carry a token;
- non-loopback `ws://` with a token is rejected before connection.

URLs embedding username/password are rejected. Diagnostic rendering strips
query strings and fragments.

## Connection deadline

Network and Unix-socket connection plus WebSocket upgrade must complete within
five seconds. Expiry fails with a bounded target-name diagnostic and cancels the
unfinished dial/handshake. This does not override the separate RPC request
timeout once the connection is established.

## Transport

One `RpcSession` implements JSON-RPC ordering, bounded queued notifications,
deadlines, server requests, search and Thread Queue semantics. Only its wire
transport varies:

- stdio: newline-delimited JSON
- TCP WebSocket/WSS: one JSON-RPC object per text/binary WebSocket frame
- Unix socket: WebSocket framing over the Unix stream, matching Codex's remote
  client protocol

This prevents protocol behavior from drifting between local and remote modes.

## TLS boundary

Codex's direct App Server listener accepts `ws://IP:PORT`, not a native
`wss://` listener. `wss://` targets therefore represent a TLS proxy/front
end in front of Codex. codex-tui treats the URL as the client endpoint and does
not attempt to configure or own that proxy.

## Platform behavior

Linux/macOS support explicit Unix-socket targets. Platforms without Unix-domain
socket support reject that target with a clear startup error; stdio and
WebSocket remain available.

## Qualification

Retained automated coverage must include:

- zero-config local target compatibility;
- TOML upgrade defaults;
- target-name override resolution;
- WebSocket URL/credential policy;
- sanitized diagnostics;
- real local WebSocket frame round trip;
- Unix-socket WebSocket frame round trip on Unix;
- Rust 1.88 and Linux/macOS/Windows canonical CI.

Real cross-machine/TLS deployment remains environment evidence, not something
CI is allowed to synthesize.
