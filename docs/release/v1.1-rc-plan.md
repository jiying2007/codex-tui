# v1.1 RC freeze and handoff plan

v1.1 is in release-candidate hardening. Product feature development is frozen while real-environment qualification is temporarily deferred.

The machine-readable authority for this phase is `release/v1.1-rc-plan.json`. It is validated against `release/v1.1-criteria.json` in CI and in the release gate.

## What continues without a real machine

Every candidate SHA must keep passing canonical CI and the exact-SHA automated qualification:

- executable Failure Matrix v2;
- 50k scale evidence;
- 50k / 256-cycle structural soak;
- Help -> keymap -> Command -> reducer UI contract;
- v1.0 -> v1.1 state migration, backup and recovery;
- Doctor Bundle privacy/source-SHA validation;
- Linux/macOS/Windows packaging and archive smoke.

Static review, release-tool correctness, evidence-schema correctness, dependency/build fixes, security fixes and data-loss/state-corruption fixes may continue. Any product-code change invalidates the current RC candidate and requires a fresh exact-SHA qualification.

Do not use this period to add new features or reopen frozen architecture work.

## Evidence intentionally deferred

Three Linux-side retained evidence items remain deferred and must not be fabricated:

1. READY `codex-tui/compat/v2` evidence from the exact candidate on the Tier-1 Linux environment.
2. PASS `codex-tui/terminal-restoration/v1` evidence from a real controlling TTY.
3. A >=200-sample `resident-planning-10k` performance diagnostic bound to the exact candidate SHA. Its p95/p99 values are retained diagnostics, not hosted-runner latency pass/fail thresholds.

A representative authenticated internal GitLab capability fixture is also deferred. It qualifies team reuse, but does not block the personal-first v1.1 stable release.

Fake binaries and CI fixtures remain useful only for testing collectors and fail-closed behavior; they are not release evidence.

## Resume procedure when real validation is convenient

Use one clean `main` exact SHA. Do not collect receipts from one SHA and publish another.

1. Confirm canonical main CI is successful for the candidate SHA.
2. Build with `CODEX_TUI_GIT_SHA` bound to that SHA.
3. Perform the real terminal-restoration smoke and create its receipt with the exact candidate identity:

   ```bash
   python3 scripts/release/create_terminal_receipt.py \
     --platform linux \
     --terminal "<your terminal>" \
     --source-sha "$(git rev-parse HEAD)" \
     --pass \
     --output release/evidence/linux/terminal-linux.json
   ```

4. Run:

   ```bash
   python3 scripts/release/linux_qualify.py \
     --canonical-ci-run <RUN_ID> \
     --terminal-receipt <REAL_TERMINAL_RECEIPT.json>
   ```

5. Review `release/evidence/linux/qualification-summary.json`.
6. Run a `stable`, `publish=false` release workflow using exactly the generated `workflowInputs`.
7. For team reuse, capture the representative internal GitLab fixture with `capture_forge_capability.py`.
8. Only after the same SHA remains qualified, finalize release notes and publish `v1.1.0`.

If any release-correctness, security, data-loss or critical compatibility fix changes product code, discard the old candidate receipts and restart from step 1.

## Exit criteria

The RC phase is complete only when:

- open release-blocking defects are zero;
- canonical CI is green on the exact candidate;
- automated qualification is green on the exact candidate;
- real Linux compatibility is READY;
- real terminal restoration is PASS;
- stable `publish=false` is green with those receipts;
- release notes and checksums are generated from the same SHA.

The internal GitLab fixture is a separate team-reuse exit criterion and may be completed after the personal-first stable gate if necessary.

## Post-v1.1 queue

After v1.1.0 is qualified and published, reopen feature evolution from evidence rather than from the old backlog by default. Keep these frozen until measurements justify them: Registry paging/new index, native GitLab REST/GraphQL, team server/RBAC, generic plugin or multi-agent frameworks, and turning Terminal Drawer into a tmux replacement.
