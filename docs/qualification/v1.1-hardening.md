# v1.1 Hardening & Qualification

This stage turns the v1.1 line into a release-candidate product rather than adding another feature layer.

## Scope

The qualification order is intentionally fixed:

1. Failure Matrix and deterministic fault injection.
2. Soak/stress structural evidence.
3. UI command-contract gate.
4. State migration and recovery qualification.
5. Secret-safe support bundle.
6. Exact-SHA preview qualification.
7. Compatibility/code-debt cleanup.
8. Stable qualification.

Real terminal/user interaction evidence can be captured in parallel. It does not block deterministic repository-internal hardening work.

## Failure contract

The machine-readable authority is `codex_tui::hardening::FAILURE_MATRIX` / `codex-tui release failure-matrix --json` (`codex-tui/failure-matrix/v2`). Every case carries one or more executable evidence identifiers; release qualification verifies those identifiers against `cargo test -- --list` before accepting the matrix.

Every external dependency failure must converge to one of:

- **Ready**: the user-visible state remains authoritative after a bounded reconcile.
- **Degraded**: read-only or partial behavior is allowed, with an explicit reason.
- **Blocked**: the operation is refused because proceeding could corrupt or misinterpret state.

A degraded or blocked dependency must never cause a panic, actor deadlock, infinite spinner, silent state replacement, or authoritative write based on stale/unknown data.

The retained matrix covers:

- app-server loss during hydration;
- malformed/timeout RPC;
- cwd/repository disappearance;
- forge authentication and CLI timeout;
- SQLite lock/write failure, corruption, and forward schema;
- truncated legacy operator state;
- abnormal PTY lifecycle;
- actor/event queue backpressure;
- concurrent registry churn during paged hydration.

## Recovery rules

Store corruption and unknown future schemas are fail-closed. The old bytes remain in place for operator recovery. Migration only archives `state-v1.json` after it parses and commits successfully.

Subprocess and RPC work has finite deadlines. Bounded queues either apply backpressure or return an explicit capacity error; they do not silently drop semantic state.

## Release evidence

The hardening workflow should retain:

- exact source SHA;
- failure-matrix test result;
- soak metrics and structural gate result;
- UI contract test result;
- state migration/recovery test result;
- support-bundle redaction test result.

Hosted-runner wall-clock variance is diagnostic evidence only. Stable release gates use structural invariants unless a benchmark has a demonstrated stable distribution.
